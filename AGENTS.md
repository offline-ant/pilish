# Pilish — Development Guide

Pilish is an Emacs frontend for the [Pi coding agent](https://pi.dev).
A session has a Markdown chat window and an ordinary prompt-editing window.
Pilish communicates with the Pi CLI through JSON-over-stdio RPC.

## Start here

- Read [README.org](README.org) for installation and user-visible behavior.
- Run `make help` for supported test, integration, benchmark, and quality targets. The [Makefile](Makefile) owns prerequisites and command details.
- Use [the verification skill](.agents/skills/verify-pilish/SKILL.md), or `/skill:verify-pilish`, to drive user-facing behavior and capture evidence. Its feature map selects the relevant journey.
- Read [the fake Pi contract](test/support/fake-pi-contract.md) before changing deterministic subprocess fixtures.
- Read each module's `Commentary` and owning tests before changing its behavior. The source tree, not this guide, is the file inventory.

## Architecture and ownership

- `pilish.el` starts sessions. `pilish-core.el` owns the process protocol. `pilish-ui.el` owns shared session state and disclosure behavior. `pilish-render.el` owns streaming, tool display, and cooling.
- `pilish-jsonl.el` reads Pi's saved data. `pilish-browse.el` owns session and tree browsers. `pilish-snapshot.el` owns independent read-only saved-conversation observers.
- Keep internal `require` dependencies acyclic. `pilish-ui.el` does not depend on `pilish-jsonl.el`. `pilish-menu.el` and `pilish-input.el` are siblings. `pilish-evil.el` is an optional leaf integration.
- Use the accessors in `pilish-ui.el` for cross-module state mutations. Direct `setq` is fine for state owned within a module.
- Loading Pilish must not make `md-ts-mode` claim unrelated Markdown buffers.
- Protocol settlement, owner-scoped rendering, cold-tool retention, and saved-conversation identity have local contracts in their owning modules and tests. Read those contracts instead of inferring behavior from event names, tool names, or output text.

## Workflow

1. Choose the owning module and the narrowest existing test. Add regressions to that suite rather than creating a parallel test layout.
2. Run focused tests during development, then `make check` before committing. Run the fake or real integration lane when the subprocess contract changes.
3. Before opening a PR, use `/skill:verify-pilish` for every changed user-facing feature and preserve its evidence. Standard tests do not replace this user-action pass.
4. When a user-facing journey changes, update the verification feature map through `/maintain-verification-skill`. Report product regressions separately from documentation drift.
5. Treat benchmark smoke targets as correctness checks. Use the primary benchmark lanes and their evidence rules for performance claims.

The unit suite runs in batch Emacs. Do not run the full unit suite inside an interactive Emacs. The GUI suite uses real frames with a deterministic fake backend. The real integration target starts Ollama.

For RPC changes, consult the Pi source that matches `PI_VERSION` in the Makefile. Its `packages/coding-agent/docs/rpc.md` and RPC implementation are the protocol reference.

## Conventions

- Prefix public symbols with `pilish-` and internal symbols with `pilish--`.
- Name tests after their owning suite, such as `pilish-test-...` or `pilish-gui-test-...`.
- Require `pilish-test-common` in module test files that use shared fixtures.
- Install the pre-commit hook with `make install-hooks`. It runs `make check`.
- Stage files explicitly with `git add <specific-files>`. Run `git status` before committing and keep test artifacts out of the commit.

## Session API contract

`pilish-start-session` creates background sessions that never display buffers, offer interactive dependency installation or prompt for missing tree-sitter grammars; a nil name selects the directory's default session and `:session-file` resumes a session with its history. Launch args/environment survive reload. Integrations register `pilish-session-environment-functions` before first spawn (failing functions are warnings). Consumers read sessions only through the public accessors in `pilish.el` (`pilish-session-directory`, `-name`, `-title`, `-file`, `-model`, `-context-usage`, `-queued-prompts`, `-extension-status`, `-busy-p`, `-exists-p`, `pilish-view-session-file`); add an accessor rather than letting integrations read `pilish--` state. `pilish-extension-status-functions` receives (chat-buffer key text) after a status changes, with nil text on clearing and on session reset. `pilish-submit-prompt` relies on Pi's own queue (`queue_update`), not Pilish's follow-up queue. `pilish-reload` calls its optional callback exactly once on every path. `pilish-restart-refusal-functions` (chat buffer → nil or a reason) forbid replacing the process, for hosts that track it: reload then runs an extension command `reload` if Pi lists one (Pi's own `/reload` is TUI-only; over RPC the text would reach the model) and otherwise settles with the reason. `pilish-session-identity-functions` receives the chat buffer when its session file, directory or buffer name changes (`pilish--note-session-identity`, run from `pilish--apply-state-response`, `pilish--retarget-session-buffers` and shared-session adoption). Pilish has no server or host-specific integration dependency. Covered by `test/pilish-session-api-test.el` (`make test-session-api`) and the reload tests in `test/pilish-menu-test.el`.

## Submission navigation

`pilish-jump-to-end-on-submit` defaults to t. `pilish--accept-input-text` returns the visible chat in the submitting frame to its end while preserving input focus. Direct drafts, steering, double-RET and local follow-ups share this path; rejected or empty input, programmatic submissions, automatic queue delivery and typing do not jump. Hidden chats stay hidden. Viewport regressions live with the answer-navigation tests (`make test-answer`).

## Chat styles

`pilish-style.el` (requires ui; render requires it) defines and implements `pilish-chat-style` (its `:set` uses `set-default`, so a `let` scopes it). `pi` decorates with overlays from a `jit-lock` function over unchanged buffer text: setext turn headings (recognized by upstream's `pilish--at-turn-heading-p` plus `pilish--style-summary-heading-re` for Compaction/Branch Summary; hidden via invisibility spec `pilish-style-heading`, which `pilish--visible-text-span-p` honours through `get-char-property`, so visible copies omit them), the `pilish-thinking-block` and `pilish-custom-message` text properties, and tool block overlays (padding strings follow the overlay face; `pilish--tool-block-finalize` flushes font-lock so they update). Emacs bug#82151 (the text property sibling of bug#80989): an overlay string containing a newline, shown at a line boundary next to text hidden by the `invisible` text property (a closing code fence, a thinking quote's `> **`, any leading Markdown markup), makes `vertical-motion` return 0, trapping `line-move`, Evil `k` and scrolling with "Beginning of buffer". Block padding therefore never puts such a string at a line boundary (workaround comment above `pilish--style-top-pad`, covered by two GUI tests). A block's bottom padding comes from its last newline: a hidden last line shows that newline, and a visible one gets a `before-string` on it with an empty `line-prefix`, which also makes the padding row a cursor stop. Don't use a `display` string on that newline: `vertical-motion` signals `args-out-of-range` when a narrowing ends there, as in `pilish--count-screen-lines-up-to`. A custom message starting with hidden text paints the blank line above it as its top padding; a tool's first line is its visible title, so it keeps a `before-string`. The decorator runs after font-lock in each jit-lock chunk so it sees which lines Markdown hides. Each pass touches only the jit-lock region, the heading owning it and the next heading; decorations are reused by kind and start, so a redraw costs the same however long the turn is (keep it that way: no widening to whole turns, no all-pairs scans). Tool block overlays are disjoint. Tool faces are remapped buffer-locally (`face-remap-set-base`). Input buffers remap `default` to `pilish-pi-user-message` (`pilish--apply-input-style`, on `pilish-input-mode-hook`). Successful tools finalize with `pilish-tool-block-success` (inherits `pilish-tool-block`, so classic is unchanged). `pilish-input-window-height` `fit` sizes input windows to the draft (`pilish-fit-input-window`, after-change timer, size-change refit); `pilish-split-input-window` is the public split used by window managers such as pi-deck. Covered by `test/pilish-style-test.el` (`make test-style`).

## Window pairs

`pilish-pair.el` (requires ui) implements the global `pilish-window-pairing-mode` and owns every pair primitive; `pilish-ui.el` only routes `pilish-split-input-window` to `pilish--pair-input-window` while the mode is on. A pair is an atomic window (`window-combination-limit` split, `window-make-atom`), both halves `side`-dedicated (the chat too, so `display-buffer` pop-ups never take it) with a `delete-other-windows` parameter (a frame-filling pair ignores `C-x 1`). The input half's `delete-window` parameter (`pilish--pair-delete-input`) closes only the input and marks the chat `pilish-lone-chat`, so Pilish's own `delete-window` calls on input windows keep their meaning; `delete-window` on the chat deletes the atom. The input half's `pilish-pair-chat` parameter records the paired chat, so the repair knows which half changed. `pilish-window-pair` and `pilish-dissolve-window-pair` are the public API. The repair (`pilish-repair-window-pairs`) runs from `window-buffer-change-functions`: marked pairs, then lone chats (stale lone inputs are deleted before any split), then lone inputs; it never guesses pairs from window shapes, so layouts restored with `window-state-put` (which drops atoms and parameters) re-pair through the lone-chat pass. It is idempotent and guarded by `pilish--repairing-pairs`. A `display-buffer-alist` entry shows session buffers in the selected pair for same-window displays. Covered by `test/pilish-pair-test.el` (`make test-pair`).

## Terminal images

`pilish-terminal-image.el` (requires ui; render requires it) shows image previews on text terminals through Kitty graphics Unicode placeholders: cells of U+10EEEE plus row and column diacritics, with the image id as 24-bit foreground color. Cells must be static compositions (`compose-string`); Emacs otherwise gives the diacritics their own columns. Each capable terminal window gets a `window`-scoped overlay over the preview label; the label's text property stays the image spec for graphical frames. Do not use a `(when COND . SPEC)` display condition instead: COND sees the selected frame, not the frame being drawn, so a graphical and a terminal frame on one chat break each other. Terminal types come from `pilish-terminal-image-types` and `tty-type`, which is what `ssh` carries; `TERM_PROGRAM` and `COLORTERM` are not available there, and plain `xterm-ghostty` already reports 24-bit color. Updates are debounced, run from `window-buffer-change-functions`, `window-size-change-functions`, `window-scroll-functions` (all buffer-local) and an `after-change-functions` entry present only while a capable window exists, and handle only previews within `pilish--terminal-image-margin` of the visible text, because `send-string-to-terminal` blocks Emacs. The image store is per terminal object (`pilish-terminal-images` terminal parameter), so a new client gets its own copy; windows of one terminal share a placement sized by the smallest. Overlays take in a closing code fence above the preview (see the newline rule under Chat styles). Replies are suppressed with `q=2`: they would arrive as keyboard input. ImageMagick sees only explicitly named JPEG, GIF and WebP input, never SVG. Covered by `test/pilish-terminal-image-test.el` (`make test-terminal-image`); the real path needs Ghostty on a display, with `TERM=xterm-ghostty` and no `COLORTERM` to match `ssh`.

## Extension dialogs

`pilish-dialog.el` (requires ui; render dispatches confirm/select/input/editor requests to `pilish--handle-extension-dialog`) owns extension dialogs: the per-process pending list (requests are event plists plus `:pilish-timer` and `:pilish-editor`), `pilish-extension-dialog-functions`, `pilish-session-pending-dialogs`, the answer/cancel commands (bound to `C-c C-a`/`C-c C-x` in chat and input maps, menu `A`/`D`) and the header segment. Core only runs `pilish--process-exit-functions`, through which pending requests close when their process exits. `agent_start` cancels older pending requests, because Pi reports no dialog it settles itself and a run's own dialogs always follow its start; on a shared process (see Shared processes) it cancels nothing. A request announced again while pending (a snapshot replay) is not asked twice and loses its `:pilish-stale` mark. Editor requests always open a separate `*pilish-editor: …*` buffer that is killed when its request closes. `pilish-extension-dialog-style` `minibuffer` (default) uses upstream's prompt helpers unchanged; `inline` appends read-only button widgets at chat end, protected from Markdown fontification by the `pilish-dialog` property in `pilish--restore-tool-properties`. Output appended after a waiting widget moves the widget back to the end (`pilish--dialog-reanchor`, debounced from `after-change-functions`). A dialog takes focus only when it follows an answer given from a widget while one of the tools running at that answer still runs (or, outside tools, while the session is idle). Pi never reports requests it settles itself: request timeouts expire them locally and Stop cancels pending requests between `clear_queue` and `abort`; a run Pi aborts without Pilish's Stop leaves its widgets until answered, cancelled or expired. Covered by `test/pilish-dialog-test.el` (`make test-dialog`).

## Shared processes

`pilish-shared.el` (requires menu; render dispatches every `pimux_*` record to `pilish--shared-handle-record`) implements the frontend side of pi-ant's `pimux` (`orchestration/pimux/README.md` there is the protocol contract), used when `pilish-executable` runs Pi through `pimux`. Core records `pimux_hello` on the process (`pilish--process-shared-p`, public `pilish-session-mux`). Dialogs close on `pimux_dialog_closed`. A snapshot sequence (`pimux_snapshot`, replayed ordinary records, `pimux_live`) rebuilds the chat synchronously at `pimux_snapshot` from its `messages`, then the replay restores work in flight through the normal handler; at `pimux_live` requests still marked `:pilish-stale` close and statuses and widgets the replay did not name clear through the normal paths (`pilish--shared-note-ui-replay`), so a status that stays never flickers for hooks. A snapshot that names another session than the chat's, whatever its reason, adopts it in place (`pilish--shared-adopt-session`: retarget, under a free number if another chat has the name, `pilish--reset-session-state` keeping the follow-up queue and prompt wait, commands refetched, identity hook); never `pilish-reload`, which starts another process. A snapshot of an active run with `run.tailTruncated` adds a chat notice and asks for a `pimux_bootstrap` when the run settles (`pilish--shared-refresh-after-run`), whose rebuild brings the full text. While Pilish's own session transition is active the snapshot only replays: the transition rebuilds. Generations only increase; older snapshots are ignored. A replayed run ends with `agent_settled` without its `agent_end`, so a snapshot of an active run sets `pilish--settle-releases-streaming`. `pimux_gap` cancels pending paints and retires the tool clock until its snapshot. A replayed `tool_execution_start` (`pilish--shared-replaying-p`) arrives long after the tool started, so it starts no estimate; Pi's recorded `durationMs` still applies at completion. `pimux_model_changed` sets the model; Pi's `thinking_level_changed` and `session_info_changed` are handled for every process. Shared processes stop with end of input (`pilish--stop-shared-process`, through `pilish--terminate-process` on close paths), so pimux tells the other frontends; killing a chat buffer also SIGHUPs its process, which pimux forwards. A session file takes one writer: other frontends can prompt a shared process until it exits, so reload stops it first (`pilish--reload-after-stop`) and the new process starts only when Pi, not just pimux, is gone (`pilish--shared-pi-running-p`, by `piPid` and the start time recorded at `pimux_hello` on the process that said it, also for a reload after the wrapper died, `pilish--exited-shared-process`). What still runs after `pilish--shared-close-seconds` is killed; if a restart fails the chat reports the process gone, draft kept. Unshared processes keep upstream's order, new process first, so a failed reload keeps the session; `test/pilish-shared-test.el` pins both. Minibuffer-style dialogs answered elsewhere leave their prompt open; answering it then does nothing. Covered by `test/pilish-shared-test.el` (`make test-shared`).

## Extension widgets and chat notices

RPC `setWidget` string lines live in `pilish--extension-widgets` (chat buffer, first-arrival key order) and show above the draft in the `before-string` of one empty overlay at the input buffer's start (`pilish-extension-widget` face), which draft edits never move; reset through `pilish--clear-extension-ui`. Every widget shows above the draft whatever its `widgetPlacement`: text after the draft would be counted by `count-screen-lines`, break the last-line test of `<down>` history, and needs a `cursor` string. `pilish-fit-input-window` adds the widgets' screen lines and measures the draft with the overlay string removed, because vertical motion also counts wrapped overlay rows. `notify` warnings and errors also append a chat notice: a run's and a compaction's output follows the buffer end through marker insertion types, so notices wait in `pilish--held-chat-notices` while `pilish--status` is `streaming` or `compacting` and are flushed after each display event and at process exit. They are literal text kept by the `pilish-chat-notice` property (its value is the face) in `pilish--restore-tool-properties`. Like retry notices they are not in Pi's history, so a chat rebuilt from it loses them. Covered by `test/pilish-render-test.el`, `test/pilish-style-test.el` and `test/pilish-session-api-test.el`.
