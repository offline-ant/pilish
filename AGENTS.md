# Pilish — Development Guide

Pilish is an Emacs frontend for the [Pi coding agent](https://pi.dev).
A session has a Markdown chat window and an ordinary prompt-editing window.
Pilish uses Pi's JSON RPC through either explicit unshared stdio or a direct
protocol-2 socket to a detached pimux runtime. Read [RUNTIME.md](RUNTIME.md) for
the versioned public API, lifetime policy and isolated native-test contract.

## Start here

- Read [README.org](README.org) for installation and user-visible behavior.
- Run `make help` for supported test, integration, benchmark, and quality targets. The [Makefile](Makefile) owns prerequisites and command details.
- Use [the verification skill](.agents/skills/verify-pilish/SKILL.md), or `/skill:verify-pilish`, to drive user-facing behavior and capture evidence. Its feature map selects the relevant journey.
- Read [the fake Pi contract](test/support/fake-pi-contract.md) before changing deterministic subprocess fixtures.
- Read each module's `Commentary` and owning tests before changing its behavior. The source tree, not this guide, is the file inventory.

## Architecture and ownership

- `pilish.el` starts views. `pilish-core.el` owns framing and RPC routing. `pilish-runtime-process.el` owns compiled-launcher receipts, socket/hello readiness and exact Pi identity; `pilish-runtime.el` owns public runtime and desktop APIs. `pilish-ui.el` owns session state and disclosure behavior. `pilish-render.el` owns streaming, tool display, and cooling.
- `pilish-jsonl.el` reads Pi's saved data. `pilish-browse.el` owns session and tree browsers; `pilish-storage.el` and its Node helper hold common stopped-file leases for managed writes. `pilish-snapshot.el` owns independent read-only saved-conversation observers. `pilish-drafts.el` owns context-bound local recovery, never runtime lifetime.
- Keep internal `require` dependencies acyclic. `pilish-ui.el` does not depend on `pilish-jsonl.el`. `pilish-menu.el` and `pilish-input.el` are siblings. `pilish-evil.el` is an optional leaf integration.
- Use the accessors in `pilish-ui.el` for cross-module state mutations. Direct `setq` is fine for state owned within a module.
- Loading Pilish must not make `md-ts-mode` claim unrelated Markdown buffers.
- Protocol settlement, owner-scoped rendering, cold-tool retention, and saved-conversation identity have local contracts in their owning modules and tests. Read those contracts instead of inferring behavior from event names, tool names, or output text.

## Workflow

1. Choose the owning module and the narrowest existing test. Add regressions to that suite rather than creating a parallel test layout.
2. Run focused tests during development, then `make check` before committing. Run the fake or real integration lane when the subprocess contract changes.
3. Before opening a PR, use `/skill:verify-pilish` for every changed user-facing feature and preserve its evidence. Standard tests do not replace this user-action pass.
4. When a user-facing journey changes, update the verification feature map through `/maintain-verification-skill`. Report product regressions separately from documentation drift.
5. Treat benchmark smoke targets as correctness checks. Use the primary benchmark lanes and their evidence rules for performance claims.

The unit suite runs in batch Emacs. Do not run the full unit suite inside an interactive Emacs. The GUI suite uses real frames with a deterministic fake backend. The real integration target starts Ollama.

For RPC changes, consult the Pi source that matches `PI_VERSION` in the Makefile. Its `packages/coding-agent/docs/rpc.md` and RPC implementation are the protocol reference.

## Conventions

- Prefix public symbols with `pilish-` and internal symbols with `pilish--`.
- Name tests after their owning suite, such as `pilish-test-...` or `pilish-gui-test-...`.
- Require `pilish-test-common` in module test files that use shared fixtures.
- Install the pre-commit hook with `make install-hooks`. It runs `make check`.
- Keep review screenshots and recordings in `tmp/` and attach them to pull requests, not Git. `assets/` contains the shipped logo, not review evidence.
- Stage files explicitly with `git add <specific-files>`. Run `git status` before committing and keep test artifacts out of the commit.

## Session API contract

`pilish-start-session` creates background sessions that never display buffers, offer interactive dependency installation or prompt for missing tree-sitter grammars; a nil name selects the directory's default session and `:session-file` resumes a session with its history. Launch args/environment survive reload. Integrations register `pilish-session-environment-functions` before first spawn (failing functions are warnings). Consumers read sessions only through the public accessors in `pilish.el` (`pilish-session-directory`, `-name`, `-title`, `-file`, `-model`, `-context-usage`, `-queued-prompts`, `-extension-status`, `-busy-p`, `-exists-p`, `pilish-view-session-file`); add an accessor rather than letting integrations read `pilish--` state. `pilish-extension-status-functions` receives (chat-buffer key text) after a status changes, with nil text on clearing and on session reset. `pilish-submit-prompt` relies on Pi's own queue (`queue_update`), not Pilish's follow-up queue. `pilish-reload` calls its optional callback exactly once on every path: nil only after both the state and history refreshes answered successfully and the transition finished; a superseded or failed reload discards its fresh process; callback errors become warnings (ported from upstream PR #404). `pilish-restart-refusal-functions` (chat buffer → nil or a reason) forbid replacing the process, for hosts that track it: reload then runs an extension command `reload` if Pi lists one (Pi's own `/reload` is TUI-only; over RPC the text would reach the model) and otherwise settles with the reason. `pilish-session-identity-functions` receives the chat buffer when its session file, directory or buffer name changes (`pilish--note-session-identity`, run from `pilish--apply-state-response`, `pilish--retarget-session-buffers` and shared-session adoption). Pilish has no server or host-specific integration dependency. Covered by `test/pilish-session-api-test.el` (`make test-session-api`) and the reload tests in `test/pilish-menu-test.el`.

## Submission navigation

`pilish-jump-to-end-on-submit` is upstream's (#388, default nil; the Phimacs config enables it). `pilish--accept-input-text` returns every window of the chat in the selected frame to its end while preserving input focus. Direct drafts, steering, double-RET and local follow-ups share this path; locally refused or empty input, programmatic submissions, automatic queue delivery and typing do not jump. Hidden chats stay hidden. Viewport regressions live with the answer-navigation tests (`make test-answer`) and upstream's input tests.

## Queued messages

`pilish-queue.el` (requires ui; render requires it) shows queued messages above the draft and takes them back. `pilish--queue-changed` is the single notification for a changed queue: local follow-up changes, the current process's `queue_update` and shared adoption call it, and `pilish--set-process` refreshes too. Lines above the draft come from `pilish--input-preamble-lines` (extension widgets, then the queue) in one `before-string`, see Extension widgets. Controls are `keymap` text properties on that string with `down-mouse-1` bound to `ignore`, so a click leaves point in the draft; the commands take the click and act on its window's session. `clear_queue` removes Pi's queue as a whole and only its response says what was removed, so nothing is taken from a displayed snapshot, and there is no per-message removal without a Pi API addition. Local follow-ups leave synchronously, so they cannot start during the round trip. A follow-up submitted as a prompt (`pilish--prompt-wait-followup`, set by `pilish--process-followup-queue`) stays until Pi answers: `pilish--take-unsubmitted-followups` leaves it. Unshared `pilish-abort` retains its ordinary Escape-style draft recovery. Shared Abort confirms before changing local work, suspends recoverable input, clears the entire shared queue once and sends Abort in wire order; a delayed Abort sends only Abort, never another unconfirmed clear. Shared clear/recover uses acknowledged requester-only recovery, not a displayed queue snapshot or per-client provenance; see [DRAFTS.md](DRAFTS.md). Pi's `clearQueue` also drops custom messages queued by extensions, which never appear in `queue_update`. Input buffers set `scroll-margin` to 0: with a margin, redisplay counts a fitted window's last row as inside it and scrolls past the lines above the draft, oscillating at each redisplay. Covered by `test/pilish-queue-test.el` (`make test-queue`) and `pilish-gui-test-queue-restore-clear-and-stop`, which clicks the real controls.

## Chat styles

`pilish-style.el` (requires ui; render requires it) defines and implements `pilish-chat-style` (its `:set` uses `set-default`, so a `let` scopes it). `pi` decorates with overlays from a `jit-lock` function over unchanged buffer text: setext turn headings (recognized by upstream's `pilish--at-turn-heading-p` plus `pilish--style-summary-heading-re` for Compaction/Branch Summary; hidden via invisibility spec `pilish-style-heading`, which `pilish--visible-text-span-p` honours through `get-char-property`, so visible copies omit them), the `pilish-thinking-block` and `pilish-custom-message` text properties, and tool block overlays (padding strings follow the overlay face; `pilish--tool-block-finalize` flushes font-lock so they update). Emacs bug#82151 (the text property sibling of bug#80989): an overlay string containing a newline, shown at a line boundary next to text hidden by the `invisible` text property (a closing code fence, a thinking quote's `> **`, any leading Markdown markup), makes `vertical-motion` return 0, trapping `line-move`, Evil `k` and scrolling with "Beginning of buffer". Block padding therefore never puts such a string at a line boundary (workaround comment above `pilish--style-top-pad`, covered by two GUI tests). The same disagreement between `vertical-motion` and the display lets terminal `scroll-down` leave point just below the view; without an intervening redisplay, as with quick wheel events, the next scroll restarts near point and the view jumps back down. `pilish--settle-command-chat-views` therefore moves point into the view after each command that moves a chat window's start (Scroll Behavior in `pilish-ui.el`, covered by `pilish-test-scroll-command-keeps-point-in-view`). A block's bottom padding comes from its last newline: a hidden last line shows that newline, and a visible one gets a `before-string` on it with an empty `line-prefix`, which also makes the padding row a cursor stop. Don't use a `display` string on that newline: `vertical-motion` signals `args-out-of-range` when a narrowing ends there, as in `pilish--count-screen-lines-up-to`. A custom message starting with hidden text paints the blank line above it as its top padding; a tool's first line is its visible title, so it keeps a `before-string`. The decorator runs after font-lock in each jit-lock chunk so it sees which lines Markdown hides. Each pass touches only the jit-lock region, the heading owning it and the next heading; decorations are reused by kind and start, so a redraw costs the same however long the turn is (keep it that way: no widening to whole turns, no all-pairs scans). Tool block overlays are disjoint. Tool faces are remapped buffer-locally (`face-remap-set-base`). Input buffers remap `default` to `pilish-pi-user-message` (`pilish--apply-input-style`, on `pilish-input-mode-hook`). Successful tools finalize with `pilish-tool-block-success` (inherits `pilish-tool-block`, so classic is unchanged). `pilish-input-window-height` `fit` sizes input windows to the draft (`pilish-fit-input-window`, after-change timer, size-change refit); `pilish-split-input-window` is the public split used by window managers such as pi-deck. Covered by `test/pilish-style-test.el` (`make test-style`).

Tool-property restoration temporarily widens during jit-lock so prefix placement can access an overlapping tool's full overlay when screen-line counting narrows inside it. Literal and header repairs retain the requested region, and the caller's restriction is restored. The real jit-lock regression lives in `test/pilish-render-test.el` (`make test-render SELECTOR=restore-tool-properties`).

## Window pairs

`pilish-pair.el` (requires ui) implements the global `pilish-window-pairing-mode` and owns every pair primitive; `pilish-ui.el` only routes `pilish-split-input-window` to `pilish--pair-input-window` while the mode is on. A pair is an atomic window (`window-combination-limit` split, `window-make-atom`), both halves `side`-dedicated (the chat too, so `display-buffer` pop-ups never take it) with a `delete-other-windows` parameter (a frame-filling pair ignores `C-x 1`). The input half's `delete-window` parameter (`pilish--pair-delete-input`) closes only the input and marks the chat `pilish-lone-chat`, so Pilish's own `delete-window` calls on input windows keep their meaning; `delete-window` on the chat deletes the atom. The input half's `pilish-pair-chat` parameter records the paired chat, so the repair knows which half changed. `pilish-window-pair` and `pilish-dissolve-window-pair` are the public API. The repair (`pilish-repair-window-pairs`) runs from `window-buffer-change-functions`: marked pairs, then lone chats (stale lone inputs are deleted before any split), then lone inputs; it never guesses pairs from window shapes, so layouts restored with `window-state-put` (which drops atoms and parameters) re-pair through the lone-chat pass. It is idempotent and guarded by `pilish--repairing-pairs`. A `display-buffer-alist` entry shows session buffers in the selected pair for same-window displays. Covered by `test/pilish-pair-test.el` (`make test-pair`).

## Terminal images

`pilish-terminal-image.el` (requires ui; render requires it) shows image previews on text terminals through Kitty graphics Unicode placeholders: cells of U+10EEEE plus row and column diacritics, with the image id as 24-bit foreground color. Cells must be static compositions (`compose-string`); Emacs otherwise gives the diacritics their own columns. Each capable terminal window gets a `window`-scoped overlay over the preview label; the label's text property stays the image spec for graphical frames. Do not use a `(when COND . SPEC)` display condition instead: COND sees the selected frame, not the frame being drawn, so a graphical and a terminal frame on one chat break each other. Terminal types come from `pilish-terminal-image-types` and `tty-type`, which is what `ssh` carries; `TERM_PROGRAM` and `COLORTERM` are not available there, and plain `xterm-ghostty` already reports 24-bit color. Updates are debounced, run from `window-buffer-change-functions`, `window-size-change-functions`, `window-scroll-functions` (all buffer-local) and an `after-change-functions` entry present only while a capable window exists, and handle only previews within `pilish--terminal-image-margin` of the visible text, because `send-string-to-terminal` blocks Emacs. The image store is per terminal object (`pilish-terminal-images` terminal parameter), so a new client gets its own copy; windows of one terminal share a placement sized by the smallest. Overlays take in a closing code fence above the preview (see the newline rule under Chat styles). Replies are suppressed with `q=2`: they would arrive as keyboard input. ImageMagick sees only explicitly named JPEG, GIF and WebP input, never SVG. Covered by `test/pilish-terminal-image-test.el` (`make test-terminal-image`); the real path needs Ghostty on a display, with `TERM=xterm-ghostty` and no `COLORTERM` to match `ssh`.

## Extension dialogs

`pilish-dialog.el` (requires ui; render dispatches confirm/select/input/editor requests to `pilish--handle-extension-dialog`) owns extension dialogs: the per-process pending list (requests are event plists plus `:pilish-timer` and `:pilish-editor`), `pilish-extension-dialog-functions`, `pilish-session-pending-dialogs`, the answer/cancel commands (bound to `C-c C-a`/`C-c C-x` in chat and input maps, menu `A`/`D`) and the header segment. Pending requests close when their process exits through upstream's public `pilish-process-exit-functions`. The fork's private `pilish--process-exit-functions` runs before the pending RPC callbacks fail, for the detached transport's quarantine (`pilish--runtime-transport-exit`), which must precede them. `agent_start` cancels older pending requests, because Pi reports no dialog it settles itself and a run's own dialogs always follow its start; on a shared process (see Shared processes) it cancels nothing. A request announced again while pending (a snapshot replay) is not asked twice and loses its `:pilish-stale` mark. Editor requests always open a separate `*pilish-editor: …*` buffer that is killed when its request closes. `pilish-extension-dialog-style` `minibuffer` (default) uses upstream's prompt helpers unchanged; `inline` appends read-only button widgets at chat end, protected from Markdown fontification by the `pilish-dialog` property in `pilish--restore-tool-properties`. Output appended after a waiting widget moves the widget back to the end (`pilish--dialog-reanchor`, debounced from `after-change-functions`). A dialog takes focus only when it follows an answer given from a widget while one of the tools running at that answer still runs (or, outside tools, while the session is idle). Pi never reports requests it settles itself: request timeouts expire them locally and Stop cancels pending requests between `clear_queue` and `abort`; a run Pi aborts without Pilish's Stop leaves its widgets until answered, cancelled or expired. Covered by `test/pilish-dialog-test.el` (`make test-dialog`).

## Detached shared runtimes

`pilish-configure-runtime` selects absolute Pi/pimux executables and protocol 2, plus the explicit task-status executable required for worker Close. `pilish-integration-capabilities` reports API version 1/protocol 2; stock Pilish's package version alone cannot establish this contract. A short-lived compiled launcher commits ownership, then Pilish connects directly as an equal Unix-socket peer. There is no primary/stdio bridge or protocol-1 lifetime shim. `pilish-session-process` is the transport; `pilish-session-runtime` and `pilish-session-process-identity` expose the actual Pi PID/start/boot identity separately. Explicit `pilish-close-session`/Quit closes the agent everywhere without confirmation; `pilish-stop-runtime` is its acknowledged root-stop primitive. Root remote authoritative termination also disposes active views; workers additionally require matching complete parent-task evidence. `pilish-runtime-task.el` owns worker evidence admission, binding preservation and read-only late reconciliation; failed/unknown evidence, and pending evidence whose owning parent is dead, retains recovery without replaying cancellation; polling is asynchronous and stops at such final uncertainty; only explicit Close retires a failed or orphaned worker that pimux's exact terminal receipt and dead processes prove ended, settling with the failure. `pilish-session-closed-functions` receives the readable chat before terminal disposal. Direct buffer disposal, frontend exit and `pilish-disconnect-session` disconnect only. Desktop restoration returns nil for authoritative terminal identities and never calls Stop as a status query. Shared reload reconnects the same runtime, never replaces Pi or resends work. Missing/uncertain runtimes retain unavailable views with explicit recovery, except verified prior-boot roots reopen idle through managed claims as specified in [RUNTIME.md](RUNTIME.md). Workers remain parent-task-owned.

The pimux protocol contract is `phimacs/packages/pimux/README.md` in the Pi workspace (`../phimacs/packages/pimux/README.md` from the `./pilish` checkout); pimux lives in Phimacs. `pilish-shared.el` applies authoritative snapshot/replay/live generations, flat entries, leaf, model, thinking and history together, including an initiating client's own transitions. Never append an independently loaded history reconstruction. Newer boundaries discard incomplete older replay; only a matching live boundary enables input. First-answer-wins dialogs close through authoritative closure, timeout or snapshot reconciliation, not a new run. Replay reconciles statuses/widgets without flicker and retires tool clocks and the run clock across gaps; a replayed `agent_start` starts no run clock, so its run settles without a return receipt. Truncated runs request a full boundary after settlement. Pi's aggregate dialog signal still cannot identify an abandoned dialog among several.

A chat whose earlier history its user need not read sets buffer-local `pilish-history-hidden-before` (epoch milliseconds, permanent-local) before its first history load; the Phimacs orchestration companion sets it to a worker's start time. `pilish--display-session-history` keeps every message canonical but draws only those at or after that time, behind one "N earlier messages not shown [show]" line; `pilish-show-hidden-history` clears it and redraws from the canonical messages once idle. Drawing a 2 MB inherited conversation otherwise blocks Emacs for about a second per worker. Covered by `pilish-test-history-hidden-before-summarizes-until-shown` (`make test-render`).

`pilish-drafts.el` quarantines text, materialized images, local automatic follow-ups and uncertain submissions when file/branch context changes. Restoring a desktop never arms saved work; explicit reuse confirms its new context. Preserve the full public desktop state and subscribe to `pilish-session-desktop-state-functions`. [DRAFTS.md](DRAFTS.md), [STORAGE.md](STORAGE.md), [MENU-RUNTIME.md](MENU-RUNTIME.md) and [RUNTIME.md](RUNTIME.md) own the detailed contracts and focused tests. Managed storage uses common fixed per-user claims, not discovery scans. Raw Pi/internal pre-I/O mutations remain an upstream safety boundary; live shared tree navigation goes through the runtime's `pimux-tree-navigate` command, and live managed label writes refuse without an owning RPC capability.

## Extension widgets and chat notices

RPC `setWidget` string lines live in `pilish--extension-widgets` (chat buffer, first-arrival key order) and show above the draft in the `before-string` of one empty overlay at the input buffer's start (`pilish-extension-widget` face, `pilish--input-preamble-overlay`), shared with the queued messages, which draft edits never move; reset through `pilish--clear-extension-ui`. Every widget shows above the draft whatever its `widgetPlacement`: text after the draft would be counted by `count-screen-lines`, break the last-line test of `<down>` history, and needs a `cursor` string. `pilish-fit-input-window` adds the screen lines above the draft and measures the draft with the overlay string removed, because vertical motion also counts wrapped overlay rows. `notify` warnings and errors also append a chat notice: a run's and a compaction's output follows the buffer end through marker insertion types, so notices wait in `pilish--held-chat-notices` while `pilish--status` is `streaming` or `compacting` and are flushed after each display event and at process exit. They are literal text kept by the `pilish-chat-notice` property (its value is the face) in `pilish--restore-tool-properties`. Like retry notices they are not in Pi's history, so a chat rebuilt from it loses them. Covered by `test/pilish-render-test.el`, `test/pilish-style-test.el` and `test/pilish-session-api-test.el`.

## Upstream relation (fork)

This is our own fork, rebased on upstream when upstream has changes worth taking. The workspace document `pilish-upstream.md` (`../pilish-upstream.md` from the `./pilish` checkout) owns its refs, rebase policy and notes, the upstream contribution state and the plan for moving the pimux layer and add-ons into dependent packages. Upstream owns merged editor dialogs (#361), fitted input (#362), compound redraw (#370), header placement (#373), image specs without a graphical frame (#379), kill unlinking (#382), thinking-level and session-name events (#383), steering sends and `M-RET` follow-ups (`pilish-send-while-busy`, #384), `pilish-jump-to-end-on-submit` (#388), the public process event, exit and unhandled-event hooks (#394), stale state guards (#406), the Markdown source toggle (#409), short completed thinking (`pilish-thinking-fold-min-lines`, width-weighted rows) and the base of `pilish-jump-to-answer` (#365); do not restore duplicate fork implementations. Pending/inline dialogs integrate with upstream's single editor in `pilish-render.el`; fitting adds only the widget/queue preamble and the public pair split. The fork keeps its pimux records (`pimux_hello`, `pimux_exit`, `pimux_*` display records) in core and render instead of upstream's event hooks, because their errors must reach the filter's detached-protocol recovery, which the hooks report and swallow.

Fork-only behaviour beyond #365: each completed answer lands following windows once without moving scrolled-back readers, at settlement after the return receipt (#376), since a run can end several low-level turns and the receipt would otherwise push a just-fitting answer's start out of view; `pilish--answer-start` never treats the receipt as an answer. The same `pilish-jump-to-answer` option positions the selected frame on session focus: the latest final answer can land again, and active work follows the output. Chat/input moves, minibuffer use and pending dialogs do not trigger positioning. `pilish-position-session-on-focus(chat-buffer)` lets workspace UIs report explicit focus before redisplay; it never displays hidden chats or changes selection/drafts. The latest final answer is retained while the option is off, so enabling it after completion works on the next focus.

Other fork-only features: the reload callback, background-session API, pending/inline dialogs, window pairs, the `pi` chat style, `pilish-send-on-double-return` (RET runs `pilish-newline-or-send`; a quick second RET at the draft end sends), `pilish-input-arrow-history` (Pi-style `<up>`/`<down>` through filtered `menu-item` bindings that fall through to the usual commands), seeding prompt history from shown session history (`pilish--seed-input-history`), queued messages above the draft, extension widgets, lasting chat notices and the extension status accessor and hook. The input status line's model and thinking click maps (`pilish--header-click-map`) also bind `mode-line` clicks, so users can show the status as the input's mode line.
